# RateLimitPolicy response customization

- Feature Name: `ratelimitpolicy-response-customization`
- Start Date: 2026-09-25
- RFC PR: [Kuadrant/architecture#0000](https://github.com/Kuadrant/architecture/pull/0000)
- Issue tracking: [Kuadrant/kuadrant-operator#2323](https://github.com/Kuadrant/kuadrant-operator/issues/2323)

## Summary

[summary]: #summary

Add support for customizing the HTTP response returned to clients when a request is rate-limited (`OverLimit`). This includes the HTTP status code, status message, response headers, and response body. The API mirrors the `response.unauthenticated` / `response.unauthorized` design already present in `AuthPolicy`, providing consistent UX across Kuadrant policies.

## Motivation

[motivation]: #motivation

When Limitador determines a request exceeds a configured rate limit, the wasm-shim returns a hardcoded `429 Too Many Requests` response with a plain-text body (`Too Many Requests\n`). There is currently no supported way to customize this response.

Users building APIs often need to return structured error responses (e.g. JSON envelopes) from all gateway-controlled rejections. Today, the only workaround is an Istio `EnvoyFilter` with `local_reply_config`, which is unsupported, fragile across upgrades, and not portable across gateway providers.

`AuthPolicy` already supports full denial response customization via `spec.rules.response.unauthenticated` and `spec.rules.response.unauthorized`, backed by Authorino's `DenyWithSpec`. The same capability should be available for rate-limit rejections.

### Goals

1. Allow users to configure the response body, headers, and status code returned on `429` (rate limit exceeded) via the `RateLimitPolicy` API.
2. Maintain API consistency with `AuthPolicy` — same field names, same `ValueOrSelector` semantics.
3. No changes to Limitador required.

## Guide-level explanation

[guide-level-explanation]: #guide-level-explanation

A new optional `spec.response.overLimit` field is added to `RateLimitPolicy`, using the same `DenyWithSpec` shape as AuthPolicy's `response.unauthenticated` / `response.unauthorized`.

### Example: static JSON error body

```yaml
apiVersion: kuadrant.io/v1
kind: RateLimitPolicy
metadata:
  name: api-rate-limit
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: api
  limits:
    global:
      rates:
      - limit: 100
        window: 1m
  response:
    overLimit:
      code: 429
      headers:
        content-type:
          value: application/json
      body:
        value: |
          {"code":"RATE_LIMIT_EXCEEDED","message":"Request rate limit exceeded","status":429}
```

### Example: dynamic body using CEL expression

```yaml
  response:
    overLimit:
      code: 429
      headers:
        content-type:
          value: application/json
      body:
        expression: >
          '{"code":"RATE_LIMIT_EXCEEDED","path":"' + request.path + '","status":429}'
```

### Behaviour without `spec.response`

When `spec.response` is omitted, the behaviour is unchanged: the wasm-shim returns the current hardcoded `429 Too Many Requests` plain-text response.

## Reference-level explanation

[reference-level-explanation]: #reference-level-explanation

### API changes

`RateLimitPolicySpecProper` gains a new optional `Response` field:

```go
type RateLimitPolicySpecProper struct {
    MergeableWhenPredicates `json:""`
    Limits map[string]Limit `json:"limits,omitempty"`
    // +optional
    Response *RateLimitResponseSpec `json:"response,omitempty"`
}

type RateLimitResponseSpec struct {
    // Customizations on the response when the request is over the rate limit.
    // Default: 429 Too Many Requests with plain-text body.
    // +optional
    OverLimit *DenyWithSpec `json:"overLimit,omitempty"`
}
```

`DenyWithSpec` is shared with AuthPolicy (same type, same `ValueOrSelector` semantics):

```go
type DenyWithSpec struct {
    Code    DenyWithCode          `json:"code,omitempty"`
    Message *ValueOrSelector      `json:"message,omitempty"`
    Headers NamedValuesOrSelectors `json:"headers,omitempty"`
    Body    *ValueOrSelector      `json:"body,omitempty"`
}
```

`ValueOrSelector` supports:
- `value` — static raw value (string or JSON)
- `selector` — gjson path into the request/auth JSON context
- `expression` — CEL expression evaluated at request time against available request attributes

### Implementation

The 429 body is generated by the wasm-shim in `process_rl_response` after receiving an `OverLimit` code from Limitador. The Envoy rate limit service protocol (`envoy.service.ratelimit.v3`) carries no body field in `RateLimitResponse` — only `overall_code` and `response_headers_to_add`. The customization is therefore applied entirely in the wasm-shim, driven by configuration injected by the operator.

**kuadrant-operator:**
- Reads `spec.response.overLimit` from `RateLimitPolicy`
- Serializes the response config into the `WasmPlugin` config JSON generated for each gateway
- The response config is scoped per action set (per policy)

**wasm-shim:**
- Extends `Service` or `ActionSet` config structs with an optional `overLimitResponse` field
- `process_rl_response` reads the configured values (status code, headers, body) when present, falling back to the current hardcoded defaults when absent
- CEL expressions are evaluated at request time using the existing CEL evaluator and request attribute context
- No changes to the pipeline or task graph are required; `SendReplyTask` already accepts arbitrary status code, headers, and body

### Merging behaviour

`spec.response.overLimit` follows the same defaults/overrides merging semantics as `spec.limits`. A Gateway-level `RateLimitPolicy` can set a default response that is overridden by a more specific HTTPRoute-level policy.

## Drawbacks

[drawbacks]: #drawbacks

- The `selector` field of `DenyWithSpec` references the Authorino authorization JSON context, which does not exist in the rate limit path. Selectors that reference `auth.*` keys will not resolve. Only request-scoped attributes and CEL expressions are applicable. This divergence from AuthPolicy should be documented clearly.

## Rationale and alternatives

[rationale-and-alternatives]: #rationale-and-alternatives

### Alternative: EnvoyFilter with `local_reply_config`

Configuring an Istio `EnvoyFilter` with `local_reply_config` can intercept and rewrite wasm-shim-generated local replies. This works technically but is unsupported, Istio-specific, fragile across upgrades, and does not integrate with policy merging. It is the current workaround but not a viable long-term solution.

### Alternative: Limitador protocol extension

The Envoy rate limit service protocol could be extended to carry a response body in `RateLimitResponse`. This would require changes to Limitador, the wasm-shim, and potentially the protocol itself. It is significantly more complex and broader in scope than necessary.

### Why mirror `DenyWithSpec` from AuthPolicy

Reusing the same type ensures consistent UX across policies, reduces API surface, and shares documentation and mental model with `AuthPolicy`. Users already familiar with `response.unauthenticated` will understand `response.overLimit` immediately.

## Prior art

[prior-art]: #prior-art

- `AuthPolicy.spec.rules.response.unauthenticated` / `.unauthorized` — Authorino's `DenyWithSpec`, which this RFC mirrors
- [Envoy local reply configuration](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_conn_man/local_reply) — the mechanism currently used in workarounds

## Unresolved questions

[unresolved-questions]: #unresolved-questions

- Should `selector` support be included in the initial implementation, or deferred? (Selectors referencing request attributes are applicable; `auth.*` selectors are not.)
- Should `spec.response.overLimit` be allowed at the `defaults` / `overrides` level in the same way as `limits`?
